# Codex/Claude account launchers

`install.sh` links both commands into `~/.local/bin` (or `PREFIX/bin`); no sourcing is required. Each launcher follows its own symlinks to the kit and runs its Python standard-library modules from the kit's `lib/`. They require Python 3.11+, install no dependencies, implement no OAuth flow, and run no background service: the helper processes of [protected mode](#usage-reserves) belong to one launch and end with it.

Paths below use the configured values: `<codex_home>` (default `~/.codex`) and `<secrets_dir>` (default `~/.secrets`). `codex-as --show-config` and `claude-as --show-config` print the values in effect; [configuration](configuration.md) describes the file that changes them.

## Daily use and adding accounts

```sh
codex-as ayting
codex-as work resume --last
codex-as ayting exec --json "Check the tests"
claude-as work
claude-as work -p "Check the tests"
codex-as --reserve-5h 10 --reserve-weekly 40 work
claude-as --enroll-native personal
claude-as --reserve-weekly 30 personal
```

Valid local credentials launch immediately. A missing account lists existing accounts and asks `[y/N]`, defaulting to no, without correcting similar names. After confirmation, successful native login, and saving, the original command continues. Corrupt files, broken links, and permission errors are not treated as missing accounts and are never overwritten for a fresh login.

- **Codex**: runs `codex -c 'cli_auth_credentials_store="file"' login --device-auth` in a private, empty temporary `CODEX_HOME`. Device login must be enabled in the account's Security settings or by the workspace admin. Failure, cancellation, or timeout does not save credentials or automatically switch to a browser flow. Use the official URL/code to complete authorization initiated on this machine. [Official authentication documentation](https://learn.chatgpt.com/docs/auth)
- **Claude**: runs `claude setup-token` in a temporary `CLAUDE_CONFIG_DIR`; there is no `generate` subcommand or equivalent device-code flow. Automatic browser opening is temporarily disabled, and the native manual authorization link is displayed. If the page returns a code, paste the complete `code#state` and press Enter. Browser cookies are not isolated by the CLI configuration directory; choose the intended account in the browser.
- Claude has no machine-readable token export interface. The local `2.1.296` adapter captures the complete success section, deduplicates it, and saves only after a successful exit, without replaying raw output. It streams ANSI/OSC sequences, chunks, and line breaks with bounded buffering. An unknown version, capture error, or failure prompts separately to run the official command and paste without echo; the default is no. **In the manual fallback, the official command displays the token; the wrapper's paste input does not echo it.**

Claude setup-token tokens typically last one year and do not renew automatically. They support model requests, with no guarantee for Remote Control or claude.ai connectors; local MCP remains usable. [Official documentation](https://code.claude.com/docs/en/authentication)

Confirmation and login I/O use a separate `/dev/tty`, preserving the final stdin/stdout/stderr, cwd, arguments, and exit code. A missing account is refused without a controlling terminal; there is no `--yes`. The wrapper's [own options](#own-options), and `codex-as NAME` with a root help or version flag, `help`, `update` or `completion`, run without the account and never start a login.

## Own options

Each launcher has a few options of its own. They count only as the first argument, by exact match and with exactly the arguments shown; everything after `NAME` goes to the native CLI. An account name never starts with `-`, so an own option never meets a native one.

| Option | Alias | Output |
| --- | --- | --- |
| `-h`, `--help` | | the help, also for a run without arguments (which exits 2); later arguments are ignored |
| `-V`, `-v`, `--version` | | the kit's release and install form; `NAME --version` is the native CLI's |
| `-l`, `--list` | `--list-accounts` | the account names, one per line |
| `--labels` | `--account-labels` | `NAME<TAB>LABEL` lines, the descriptions of the zsh completions |
| `-i NAME`, `--info NAME` | `--account-info NAME` | the last-seen details of one account ([account metadata](#account-metadata)) |
| `--show-config` | | the configuration in effect ([configuration](configuration.md)) |
| `claude-as --label NAME [LABEL]` | `claude-as --set-label NAME [LABEL]` | sets a Claude label, asks for it, or clears it with an empty one |
| `claude-as --enroll-native NAME` | | enrolls a Claude account with Claude Code's own login ([native login](#claude-native-login)) |

The aliases are accepted too; the help lists only the primary spellings. `-h` and `--help` ignore any later arguments; any other own option with arguments beyond its own is an invalid account name. Any other dash word in the first argument is refused with a hint and the exit status of an invalid account name (2 for `codex-as`, 1 for `claude-as`), and nothing starts or is written. The hint echoes only the part before the first `=`, since a value or a secret may follow it; a word with characters other than ASCII letters, digits and `_=.,:/@+-`, or whose part before `=` holds `sk-` in any case or names an own option, gets the plain invalid-name message instead, so it is never echoed:

```text
$ codex-as -c model=o3
codex-as: -c is not a codex-as option; native options go after NAME (codex-as NAME -c ...)
```

`--reserve-5h V` and `--reserve-weekly V` are launch flags, not queries: they set this launch's [usage reserves](#usage-reserves) and come before `NAME`, in either order, each at most once, with the value as the next argument (`V` is a number from 0 through 100, or `off`). They are exact words: `--reserve-5h=10` is refused, and after `NAME` both go to the native CLI like any other argument. Their errors exit 1 and start nothing:

```text
codex-as: --reserve-5h takes a number from 0 through 100, or off, as the next argument.
codex-as: --reserve-5h is given twice.
codex-as: --reserve-5h=VALUE is not accepted; write --reserve-5h VALUE.
codex-as: an account name must follow --reserve-5h and --reserve-weekly.
```

`--version` is plain shell, like the help: it needs no `python3` or `git`, starts no native CLI, writes nothing and is never styled. It prints `coding-agent-kit X.Y.Z (FORM)` on stdout, where `X.Y.Z` is the release written into the launcher and `FORM` comes from the directory the launcher resolves to after its links:

| FORM | When |
| --- | --- |
| `managed vX.Y.Z, channel X.Y` | the directory is `vX.Y.Z` in a `releases` directory, as in a managed install; the channel comes from the managed root's `channel` file and is left out when that is missing or malformed |
| `checkout ROOT` | `ROOT/.git` exists: a clone, a worktree or a submodule |
| `files ROOT` | anything else, such as copied files |
| `unknown` | the launcher cannot resolve its own location |

A session started before a managed update keeps its release, and that release's launchers keep printing it. A checkout between tags prints the release its launchers name, the first heading of its CHANGELOG, and no commit.

```text
$ codex-as --version
coding-agent-kit 0.7.0 (managed v0.7.0, channel 0.7)
```

## Usage reserves

A usage reserve keeps part of an account's subscription allowance unused. Each of the two windows, the 5-hour and the weekly limit, has its own reserve, a percentage of the window that should stay left; they are never combined. Set them for one launch with `--reserve-5h V` and `--reserve-weekly V` before `NAME`, or for every launch, globally or per account, in the [configuration file](configuration.md#usage-reserves). For each window the flag wins, then the account's table, then the global value; the default is off. A flag changes only that launch.

```sh
codex-as --reserve-5h 10 --reserve-weekly 40 work   # keep 10% of the 5-hour and 40% of the weekly limit
claude-as --reserve-weekly 30 personal              # the 5-hour window inherits, or stays off
codex-as --reserve-5h off --reserve-weekly off work # an unprotected launch, whatever the file says
```

With both windows off, as by default, a launch is exactly what it is without this feature: the same arguments, environment and process. So are `NAME --help` and `NAME --version`, for codex-as also `NAME help`, `update` and `completion` and a subcommand's own help, and every launch of an older kit, which ignores the configuration tables with a warning (0.8.0 is the first release with reserves). With a reserve on, the launch runs in protected mode, or it is refused before anything starts:

```text
codex-as: usage reserve protection refused: REASON. (--reserve-5h off --reserve-weekly off launches unprotected)
claude-as: protected mode refused: REASON.
```

A refusal exits 1. The session never started and no model request was sent, though the native CLI's version query and its pre-launch refresh may have run, inside the boundary (below); whatever they started has been ended. The reason names the cause without values: an option, a command, an environment variable, a host property, a policy key. Fix it, or launch without reserves. A few claude-as refusals come before protected mode and keep the launcher's own wording, also exit 1: a reserve on a setup-token account (`usage reserves need a native-login account, ...`), an account configured for native login but not enrolled, or whose enrollment is pending, and the argument and environment checks every launch runs.

A reserve is an observation, not a reservation the provider enforces. Requests already in flight, other clients of the account and the provider's reporting delay can use more than the reserve leaves before the pause takes effect, and no exact remaining percentage or largest overshoot is promised. Two protected launches of one account each pause at their own reserve; usage from anywhere else still counts against the account, and nothing is locked account-wide.

### Protected mode

Protected mode runs the native interactive TUI as usual, with its model requests routed through a local request gate that stops admitting them when the account reaches a reserve. A launch:

1. Runs every check that needs no change: the host, the arguments, the environment, the account (its login, plan and policy), and where the kit, its Python and the native lie. Codex reads its version here, with `codex --version` inside a boundary of its own (nothing writable, no network). See [requirements](#protected-mode-requirements).
2. Holds a random loopback port, the gate port, for the whole run. Claude Code reads its version now, with `claude --version` inside the boundary, after the macOS self-test. The native never runs outside the boundary, and only a reviewed release passes.
3. Lets the native CLI refresh the account's credential before any model work, confined behind a refresh gate that passes only the provider's sign-in host and, for Codex, the workspace configuration bundle (Codex: an App Server account read with a token refresh, behind `auth.openai.com:443`; Claude Code: `claude auth status`, behind `platform.claude.com:443`). It is refused if that fails. Codex refreshes, and so rotates the refresh token, on every protected launch. Claude Code renews its token only when less than five minutes remain, and `claude auth status` exits 0 whether or not it renewed anything, so the gate checks the token itself afterwards: the launch is refused when the token still expires within five minutes (the refresh did not renew it) or within fifteen minutes (too short a session; launch again in up to ten minutes, once fewer than five minutes remain and the pre-launch refresh renews it), and the launcher then names the time the token expires. No renewal passes the gate once a Claude Code session runs, so it needs a relaunch by then, unless another session of the account renews the token, which the protected session then adopts through the gate.
4. Starts two helper processes outside the boundary, the gate on the held port and a monitor that keeps it alive and drives its quota reads, and requires one fresh read of both windows of this account, attributed to it and above both reserves. That read sends no model request.
5. Starts the native on a terminal of the launcher's own inside an OS boundary whose only intended network exit is the gate (on Linux the boundary limits the port number, not the address; see the [network cost](#what-protected-mode-costs)), with the native's own tool sandbox turned off (the boundary and its write rules replace it), and prints the reserves in effect and where each comes from:

```text
codex-as: usage reserves for work: five-hour 10% (--reserve-5h), weekly 40% (usage_reserve.codex_accounts.work)
```

While it runs, the gate admits a model request only when it carries the account's credential, names a model of the account's quota family that this release has reviewed, and the last quota reading is fresh and above both reserves. It reads quota about every 30 seconds, every 15 seconds while a window is within 10 points of its reserve, and caps its own reads at 10 a minute; the first read after the start-up check comes about a minute later, for both tools. The gate is the only process that talks to the provider about quota. It connects through the proxy the native itself would use for HTTPS, captured once at start-up: `HTTPS_PROXY` (or `https_proxy`), otherwise, for Codex, on macOS the system HTTPS proxy ([protected Codex](codex-as.md#protected-mode)) and then `ALL_PROXY` (or `all_proxy`), and for Claude Code `HTTP_PROXY` (or `http_proxy`), then `ALL_PROXY`. Only a plain `http://HOST:PORT` proxy works; any other value, or two spellings of one variable that differ, refuses the launch instead of connecting directly. The gate reaches a provider host directly only where both natives read `NO_PROXY` as exempting it: the value `*`, the exact host name, or `.DOMAIN` for a host below DOMAIN, in each of `NO_PROXY` and `no_proxy` that is set (an empty one exempts nothing, as Codex reads it). An entry with a port, an address range or a `*.` prefix, or names separated by spaces instead of commas, keeps the host on the proxy. The native never sees the proxy.

### Pause and continuation

The gate pauses when the remaining percentage of an enabled window, 100 minus the provider's own unrounded usage, is at or below its reserve. It also pauses, instead of carrying on unprotected, when it cannot tell: no fresh passing reading for 120 seconds (failed reads never extend this), a missing, malformed or unattributed window, another account signed in, an unreviewed plan or quota family, Codex reporting a usage limit reached (`limit_reached` or `allowed` false) that no window at 100% accounts for (an exhausted window whose reserve is off is ignored), the monitor stopped or silent for 1.5 seconds, or the gate itself stopped. A pause refuses every new model request and closes the streams and tunnels it admitted; the native shows the refusal, `quota reserve: model requests are paused (REASON); continue from the launcher terminal after a fresh quota check`, as a request error (HTTP 503 for Codex, 400 for Claude Code, never 401, which would make the native try to refresh its login), and its interface stays usable for reading history. The launcher writes one line into the terminal:

```text
[coding-agent-kit] quota reserve paused (threshold); account work; window five-hour; remaining 9.5% (reserve 10%); resets 2026-11-12T14:30:00Z; last fresh check 2026-11-12T14:02:11Z; press F12, then type the code shown and Enter, to request a fresh check
```

The remaining percentage is rounded down to one decimal, and times are UTC. A pause for another reason names it, and the window and percentages when there are any.

Nothing resumes by itself: a window reset, a passing poll, a queued prompt, a hook or a background task never restarts model work. While paused the gate keeps reading quota, every 60 seconds and backing off to every 5 minutes, for as long as the pause lasts. When the latest reading starts to pass, the launcher writes a line that resumes nothing:

```text
[coding-agent-kit] quota reserve: the latest quota check passes; account work; last fresh check 2026-11-12T14:31:05Z; press F12, then type the code shown and Enter, to continue
```

When the readings stop passing again, it writes the pause line with the new reason. It writes at most one such line every 30 seconds. A failed read starts no such line, and drops a passing line that the 30-second limit still holds back; a passing line already shown stays the last one while later reads fail, and pressing F12 then says why the session is still paused.

To continue, press F12: the launcher shows a fresh one-use code; type it and press Enter. That asks for one new quota read, and the gate resumes only if it arrives within 30 seconds, every enabled window passes and the monitor is alive. Otherwise it stays paused with the reason, the code is used up, and F12 gives a new one. Input typed before the pause is discarded, a paste never confirms, the native's output never reaches the launcher's parser, an old code or a repeated F12 grants nothing, and Ctrl-C cancels the code and reaches the native. While the check runs the launcher relays nothing: the native's output, typed keys and window size changes wait until it answers, up to about 40 seconds (Codex's check starts a quota reader). A check that does not answer in time is cancelled, and the launcher says `still paused: gate_unavailable`; if it passed just before, the launcher says so and model requests resume.

Reserves change only at launch: to lower one after a pause, exit and launch again with new flags (`--reserve-5h off --reserve-weekly off` launches unprotected). The native refreshes its credential only before the launch, since the sign-in host is unreachable inside the boundary: once the access token expires, model requests fail or pause and continuing cannot help. Exit and launch again, which refreshes it.

A gate that stops is restarted, paused, on the same port, which the launcher keeps: a request sent meanwhile waits and is then refused, and pressing F12 while it is down answers `still paused: gate_unavailable`. After 5 restarts within 10 minutes the gate stays down, still paused, and the launcher says to exit and relaunch; it restarts the gate again once the oldest of those restarts is 10 minutes old.

### Terminal, signals and exit

In protected mode the launcher stays running instead of exec'ing the native: it owns your terminal, runs the native on a terminal of its own, forwards input, output, window size changes and signals, and exits with the native's exit status, or by the same signal. The native leads its own session there, so its own suspend key does nothing, a native that stops itself is continued, and Ctrl-Z reaches it as a key; the launcher itself is never suspended.

When the native exits, the launcher ends every process still running inside the boundary, background tools and detached descendants included, for up to 5 seconds (on Linux as their child subreaper; on macOS through the session and snapshots taken every second with the system `/bin/ps`, never a `ps` found through `PATH`, which a process that calls `setsid` between two snapshots escapes; a Codex quota reader that is running when the gate restarts or the launch ends is missed there too, and stays confined, with only the released gate port, until its read fails or its own 45-second limit ends). It signals the process groups of the boundary's sessions as a whole, so a process that forks and exits in a loop is ended too: on Linux also in a process group of its own, through the exited members the launcher holds until it collects them, unless the loop changes its process group on every fork; on macOS only in its session's own process group. The launcher then stops the gate and the monitor, releases the port and removes its private temporary directory. If the launcher itself is killed, the gate, the monitor and the native end with it, but a descendant that detached from the native can keep running, without network beyond the dead gate port.

Background tools keep running through a pause, with the same gate-only network. On Esc, Codex keeps a running foreground tool going in the background and Claude Code ends it.

### Protected mode requirements

| | Supported | Refused |
| --- | --- | --- |
| Linux | x86_64 with Landlock ABI 6 or newer (kernel 6.12 and newer kernels that keep it enabled) and seccomp | WSL, other architectures (aarch64 included), Landlock missing, disabled or older than ABI 6 (the Ubuntu 24.04 GA kernel 6.8 has ABI 4), no seccomp, standard input, output or error that is a socket |
| macOS | macOS 27.2 (any 27.2.x update) on Apple silicon, with `/usr/bin/sandbox-exec`, `ifconfig` and a root-owned `/bin/ps`, and a startup self-test that passes | every other release, older ones such as macOS 15 as well as newer ones such as 27.3 or 28 (unreviewed); Intel Macs; a missing tool; a failing self-test |
| Codex | codex-cli 0.167.2, the interactive TUI, an account with a saved login and a SQLite home in which Codex has created its databases | other releases, older and newer ones and suffixed versions; every subcommand but help, update and completion; a `codex` (or its `#!` interpreter) inside a path the boundary can write; a `PATH` entry the boundary can write, or a relative or empty one, before the one that supplies `python3`, `codex` or that interpreter; a shared state entry in `<codex_home>` that is a link; an account without a saved login; a SQLite home without the databases Codex creates; see [protected Codex](codex-as.md#protected-mode) |
| Claude Code | 2.1.322, the interactive TUI, a `native-login` account with a Pro or Max subscription; a Claude Code program, its directory and its `#!` interpreter outside every path the boundary can write; no empty, relative or boundary-writable `PATH` entry among those that supply `dirname`, `readlink`, `python3`, `claude` and the command of its `#!/usr/bin/env` line, or before them | other releases, older and newer ones; setup-token accounts; organization accounts; print, resume, remote and every subcommand; a Claude Code installed in the project or the account directory; see [protected Claude Code](#protected-claude-code) |
| Both | an interactive terminal; a working directory that is not HOME or one of its ancestors; no proxy, or a plain `http://` one, in the variables the native reads for HTTPS (`HTTPS_PROXY`, then `ALL_PROXY` for Codex, or `HTTP_PROXY` and then `ALL_PROXY` for Claude Code, either spelling; for Codex on macOS also the system HTTPS proxy between the two, without automatic proxy configuration); the launcher's `python3`, its prefixes and module path, and the kit outside every path the boundary can write, with no empty, relative or boundary-writable `PATH` entry before the one that supplies that `python3` | the environment variables that select another endpoint, credential or store |

Protected mode accepts only the reviewed releases: codex-cli 0.167.2, Claude Code 2.1.322 and, on macOS, macOS 27.2 with any of its 27.2.x updates. Every other release is refused as unreviewed, an older one (macOS 15, for example) as well as a newer one. Refusing newer releases is a disclosed upper bound, on purpose: protected mode relies on each release's argument parser, commands, routes and models, and a command added by a newer release would read as a prompt to an older screen. A native that updates itself therefore stops protected launches until a kit patch reviews the new release; unprotected launches keep accepting any release above the minimum. The macOS release is bounded for the same reason: the boundary uses `sandbox-exec`, deprecated and undocumented, whose profile is checked again for each release.

The boundary is the kit's own Python code, run by the launcher with nothing installed: on Linux Landlock and a seccomp filter set through `ctypes`, on macOS a Seatbelt profile rendered for the run and passed to `/usr/bin/sandbox-exec`. Without the capability, protected mode is refused, never weakened.

### What protected mode costs

- **Network**: the gate is the only intended exit, running or paused, but the two boundaries differ. On macOS only `localhost:PORT`, the gate port, is reachable, and every bind is denied. On Linux, Landlock limits TCP by port number, not address: a process inside can connect to the gate's port number at every address, local or remote (a remote host listening on that port included), and while a chosen port cannot be bound, it can bind port 0 and accept connections from outside on the port the system picks. So on Linux the boundary keeps ordinary tools off the network, but a process inside that sets out to exchange data with a party outside still can. Git over HTTPS or SSH, package managers, `curl`, `ssh`, remote notebooks, MCP servers or hooks that need the network, and local TCP servers (a development server on localhost included) fail inside the session. There is no name resolution and no ICMP, and HTTPS through the gate as a proxy is refused. Model requests reach the provider only through the gate, which uses the proxy described in [protected mode](#protected-mode).
- **Local sockets**: on Linux, creating UNIX sockets, UDP and datagram socket pairs is denied, which breaks forkserver multiprocessing (the Python 3.14 default), ssh and gpg agents, tmux, X11, Docker, file-system monitors and language servers on UNIX sockets. On macOS every bind and every pathname socket is denied.
- **Writes**: processes inside write only beneath the workspace (the working directory), the account's own directories and a private temporary directory removed at exit (Codex and Claude Code add their own; see each tool's section), and the terminal devices. Writes elsewhere fail: other repositories, `~/.gitconfig`, caches in HOME or `~/Library`, package stores. Reads and execution stay open everywhere, and on Linux so do metadata changes (`chmod`, `chown`, times, extended attributes). HOME, its ancestors, `~/Library` and `~/Library/LaunchAgents` are never writable, which is why a launch from HOME is refused. A writable path on macOS must be printable ASCII without a quote or backslash, so a workspace with an accented name is refused there.
- **Untrusted after the run**: protected mode confines the invocation, not later use of what it wrote. Everything the boundary can write is untrusted while a protected session runs and after it, and protected mode checks none of it afterwards: the workspace; for Codex the account home `<codex_home>/accounts/NAME`, the shared sessions, history, index and lock files and the databases; for Claude Code the account directory, every `--add-dir` and, on macOS, `/private/tmp/claude-UID`; the private temporary directory until its removal; and the shared devices. A process outside the boundary that later runs or loads something from there runs it unconfined, with the user's full network and files. In the workspace that includes Git hooks and repository configuration (`.git/hooks`, and `core.hooksPath`, `core.fsmonitor`, `core.sshCommand`, `core.pager`, filter, diff and merge drivers and aliases in `.git/config`), which the next `git` there runs; `.envrc` files that direnv loads; a virtual environment's scripts and `.pth` files; editor and IDE task, launch and settings files; and build and package scripts such as a `Makefile` or `package.json`. The next unprotected launch of the account loads the native's own settings, hooks, skills, plugins and MCP servers from its account directory or home; for Codex that includes the `.env` file it loads at start, the account's own plugin cache (plugins carry MCP server and hook commands), a `PROFILE.config.toml` that a later `codex-as NAME -p PROFILE` reads when `<codex_home>` has none, and, on Linux, `tmp/arg0-linux`, which an unprotected Codex of the same account running at the same time puts first on its tools' `PATH`. A native configuration file that is a link into a writable path, such as a `config.toml`, `hooks.json` or `settings.json` linked from a dotfiles repository in the workspace, becomes writable through the link. A sync root in the writable set (a Dropbox, OneDrive or Google Drive folder, or iCloud Desktop and Documents on macOS) uploads what a session writes to other machines and brings in what others put there, a two-way channel past the network boundary on both platforms, so start protected sessions outside sync roots. Review these files before using them outside a protected session, or run protected sessions only in workspaces whose contents get reviewed anyway.
- **PATH order**: a program run by name comes from the first `PATH` entry that holds it, so a directory of the writable set on `PATH` lets a session plant a program under that name, which a later run outside the boundary executes unconfined. claude-as refuses a protected launch when the entry that supplies a program it runs by name, or an entry searched before that one, is empty, relative or boundary-writable: the `dirname`, `readlink` and `python3` that `bin/claude-as` runs before any check, the `claude` it runs and the command of a `#!/usr/bin/env` line on the way to it (see [protected Claude Code](#protected-claude-code)). codex-as refuses when an entry searched before the one that supplies `python3`, `codex` (when the codex key is a command name) or the command of the native's `#!/usr/bin/env` line is empty, relative or boundary-writable, and checks the programs found there by name ([protected Codex](codex-as.md#protected-mode)); it does not check the `dirname` and `readlink` that `bin/codex-as` also runs before any check, nor a `python3` wrapper script in the supplying entry. Other commands are not checked: keep the writable set's directories (a project `bin`, `node_modules/.bin`, `.` or an empty entry) off `PATH`, or after the system directories, while you use protected mode, since a later `git`, `node` or `make`, or `claude-as` or `codex-as` itself when the shell finds it by name, would otherwise run what a session put there. A version manager's shim (asdf, mise and the like) picks the program it runs from files in the working directory and its parents (`.tool-versions`, `mise.toml`, `.python-version`, `.nvmrc`, `.node-version`), which a protected session can write: when such a shim supplies the `python3` that the launcher starts before any check, or the native or the `node` that a later launch finds, the next launch can run a program the session chose there outside the boundary, although the shim's own `PATH` entry passes the checks. While you use protected mode, supply `python3` and the native's interpreter from a fixed install rather than a shim that reads project files, or review those files after a protected session. On macOS these checks, and the reach checks of the kit, its Python and the native, compare paths as they are spelled, while a case-insensitive volume (the APFS default) also opens a path spelled in another letter case: spell `PATH` entries, the paths of the kit configuration (the `claude` or `codex` key, `codex_home`, `secrets_dir`) and `--add-dir` paths with the case the file system stores, as `ls` of the parent directory shows it, or a path of the writable set spelled otherwise can pass them.
- **Shared devices**: the terminal devices (`/dev/pts` on Linux, `/dev/ttys*` on macOS) let any process inside write escape sequences to every terminal of the user, not only its own; on Linux `/dev/shm`, for POSIX shared memory, is a temporary file system shared with every process of the user.
- **Linux**: 32-bit programs do not run inside the boundary (i386 code is killed, x32 calls fail).
- **macOS**: no setuid tools, `open` (LaunchServices), Apple Events or new launchd jobs. The Keychain service stays reachable, so processes inside can query the user's Keychain as they can outside (the gate still refuses any credential but the account's). The profile does not cover writes delegated to the preferences daemon (a process inside can have it change the user's `~/Library/Preferences` domains) or `launchctl kickstart` of existing launchd services, and access to other processes' task ports is unexamined: HOME is not read-only on macOS in every sense.
- **Native sandbox**: the native tools' own sandbox is off (Codex `danger-full-access`, Claude Code `sandbox.enabled` false), because it cannot start inside the boundary. Every process inside can write every writable directory.
- **Time and processes**: a start adds the confined version check, the pre-launch refresh (up to about a second), the start-up quota read and, on macOS, the self-test (about 40 ms). Each launch runs a gate and a monitor for its lifetime; Codex adds a short-lived App Server per quota read.

## Claude native login

A Claude account can use Claude Code's own login instead of a `claude setup-token` token. Usage reserves need it: the provider does not report a setup-token's usage, and protected mode reads the usage and identity of the account's own login. Claude Code keeps the credential and refreshes it; claude-as never stores, copies or renews it, and never offers a setup-token for such an account.

```sh
claude-as --enroll-native personal
```

The first run creates a pending registration, `<secrets_dir>/native-claude-accounts/NAME/account.json` (0600, in 0700 directories), and the account's own configuration directory beside it, then prints the two commands to run yourself in the same terminal, with the exact `CLAUDE_CONFIG_DIR`:

```text
  CLAUDE_CONFIG_DIR=<secrets_dir>/native-claude-accounts/personal/config claude auth login
  CLAUDE_CONFIG_DIR=<secrets_dir>/native-claude-accounts/personal/config claude auth status
```

After the login, run `claude-as --enroll-native NAME` again: it shows what `claude auth status` reports and asks `Use this account and organization as NAME? [y/N]`. Confirming records the account and organization the login names and marks the enrollment ready; another run then answers that the account is already enrolled. Until `[claude_auth.accounts.NAME] mode = "native-login"` is set in the configuration file, each run prints that setting too; an enrolled account appears in `--list` and `--labels` meanwhile, and launching it says to set the mode. Enrollment refuses an inherited `CLAUDE_CONFIG_DIR` and the authentication and provider variables a launch refuses, and it never runs a native login itself.

A native-login account name has at most 64 characters: ASCII letters, digits, `_` and `-`, not starting with `-`. Every directory above the account's 0700 directories (`<secrets_dir>` and its ancestors) must belong to you or root and, unless it is sticky like `/tmp`, must not be writable by other users (group write is fine only for your user private group, without an access ACL); a refusal names the directory and suggests `chmod go-w DIR`. Claude Code's `.claude.json` in the account's configuration directory follows the same rule.

A `native-login` account launches Claude Code with `CLAUDE_CONFIG_DIR` set to its own directory and no token injected; the argument and environment checks of a setup-token launch apply. Its user-level settings, `CLAUDE.md`, skills, plugins, MCP servers, history and trust state live in that directory, so nothing of the daily `~/.claude` is inherited (a project's own files still apply); Claude Code's shared device state in `~/.claude` (such as `.device-keys.json`) is still used. A `CLAUDE_CONFIG_DIR` set to another directory refuses the launch. A login that Claude Code can no longer refresh, or that was revoked, needs `CLAUDE_CONFIG_DIR=... claude auth login` again; to replace the account, remove `<secrets_dir>/native-claude-accounts/NAME` and enroll again.

### Protected Claude Code

A launch with a reserve and a `native-login` account runs Claude Code 2.1.322 in protected mode; a setup-token account is refused (`usage reserves need a native-login account, ...`). Beyond the [general requirements](#protected-mode-requirements):

- **Organization accounts are refused.** Claude Code applies an organization's server-managed policy only while it talks to its own service, and applies none while its requests go through the gate (a custom `ANTHROPIC_BASE_URL`). Protected mode does not run without that policy, so it supports Pro and Max accounts only: the gate refuses at start-up any account whose subscription type, as Claude Code recorded it in its credential store, is not Pro or Max, or is missing, and the launcher refuses every account on a machine whose managed settings pin the sign-in organization (`forceLoginOrgUUID`). The refusal comes after the pre-launch `claude auth status`, names the account and says to launch it without reserves (`claude-as NAME`); Enterprise and Team accounts launch only that way. The kit judges the recorded subscription type and does not verify it with the server. Pro and Max accounts lose nothing, since Claude Code applies no organization policy to them in any mode. No policy fetch is attempted in a protected session, so there is no fetch delay and nothing is refreshed; cached `remote-settings.json` and `policy-limits.json` in the account's directory, and the managed and local settings sources, are still judged, and a setting that would change what protected mode relies on (an authentication helper, another endpoint, credential store or proxy, environment variables of those families) refuses with its key name. Managed settings files may belong to root. None of the settings files may be writable by other users: other write refuses, and so does group write unless the group is your user private group and the file has no access ACL, the rule of the [configuration file](configuration.md#file-permissions); the refusal names the file and suggests `chmod go-w FILE`. The two cached files must be 0600, as Claude Code writes them.
- **Arguments**: only the interactive forms of 2.1.322 that claude-as audits for every native-login launch pass (`--model`, `--effort`, `--system-prompt`, `--append-system-prompt` and their `-file` forms, `--agent`, `--agents`, `--permission-mode`, `--fallback-model`, `--debug-file`, `-d`/`--debug`, the tool allow and deny lists, `--add-dir`, `--verbose`, `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--disable-slash-commands` and `--strict-mcp-config`), parsed as Claude Code parses them, with values checked by Claude Code and models by the gate. Refused: print mode (`-p`, also inside a cluster such as `-cp`), `--resume`, `--continue`, `--fork-session`, `--session-id`, `--settings`, `--setting-sources`, `--mcp-config`, `--plugin-dir`, `--plugin-url`, remote, cloud, teleport, desktop, Chrome, IDE, tmux, worktree and background options, `--betas`, and every top-level command, visible or hidden, aliases included, as the first operand. To resume or continue a conversation, launch without reserves: `/resume`, `/new` and `/fork` inside a protected session are not verified behind the gate.
- **Environment**: variables that select another credential store, endpoint, transport or process wrapper refuse, by name.
- **Inside the session**: model requests go to the gate (`ANTHROPIC_BASE_URL`), with `HTTPS_PROXY` at the gate and `NO_PROXY=127.0.0.1`; the native sandbox and `remoteControlAtStartup` are off, and `CLAUDE_DISABLE_ADOPT=1` removes "Move to background and exit" from the exit dialog, so background tasks end with the session. The writable set is the workspace, the account's directory, a private `TMPDIR` and every `--add-dir`; on macOS also Claude Code's fixed `/private/tmp/claude-UID`, whose entry for this working directory is removed at exit when it did not exist before (a same-directory session started meanwhile may share it, and an entry that existed before keeps what this run wrote). The launcher records that directory just before the native starts, creating it (mode 0700) when it is absent, and at exit removes the entry by descriptor beneath that same directory only, so a boundary process that replaces the directory or the entry with a link makes the cleanup remove nothing. Claude Code's own policy refresh and auxiliary calls (profile, bootstrap, telemetry) are refused at the gate without a visible error. Hooks, stdio MCP servers and plugins run inside the boundary and reach only the gate.
- **Kit processes**: the gate and the monitor run outside the boundary, so nothing they load code from may be writable from inside: they run the base interpreter of the Python that runs claude-as, and a launch is refused when that interpreter, its prefix, a module path entry or the kit's directory, or a link on the way to one, lies inside a path the boundary can write (the writable set above and the boundary's devices), or such a path lies inside a module path entry or the kit's directory (`run claude-as with a Python and a kit installed outside the working directory, every --add-dir and the account directory`). A kit checked out inside the project, as a submodule for example, therefore cannot launch with reserves from that project. The launcher itself runs as the `python3` found on `PATH`, started as `python3 -I -B -S`, so no site-packages or `.pth` file of that Python runs in it, and a launch is refused when that `python3` (by the name found on `PATH`, through every link), its prefix or a module path entry lies inside a path the boundary can write (`the launcher's Python PATH lies inside DIR, which the boundary can write; start claude-as with a python3 outside the working directory, every --add-dir and the account directory first on PATH (deactivate a workspace virtual environment)`), since a protected session could replace it under the next launch. The native itself never runs outside the boundary: its `--version` check, the pre-launch refresh and the session all run confined. A launch is refused when the Claude Code program (by the name the launcher runs, through every link), its directory, or an interpreter its `#!` line names (an absolute one, or the command a `#!/usr/bin/env NAME` line finds on the native's `PATH`, such as `node`, through nested scripts) lies inside a path the boundary can write, or such a path lies inside the program's directory (`the Claude Code program PATH lies inside DIR, which the boundary can write; run claude-as with a Claude Code installed outside the working directory, every --add-dir and the account directory (the claude key of the kit configuration can name it), and its interpreter too`), since a protected session could replace it under the next launch and every later unprotected launch would run it unconfined. A project-local Claude Code (`node_modules/.bin/claude`), one kept in the account directory, or one whose `node` lies in the working directory therefore cannot launch with reserves; a `#!` line with an `env` option other than `-S`, a `PATH=` assignment, a relative interpreter or more than four nested interpreters is refused too. Programs run by name come from the first `PATH` entry that holds them, so a launch is also refused when that entry, or an entry searched before it, is empty or relative (the working directory, or a path relative to wherever claude-as starts) or lies inside a path the boundary can write, by any name on the way to the program in it. This holds for the `dirname` and `readlink` that `bin/claude-as` runs to find its own directory and the `python3` it starts, all before any check, for the `claude` the launcher runs (when the claude key is a command name) and for the command of a `#!/usr/bin/env` line on the way to it (`the PATH entry DIR, searched for python3 before ENTRY, lies inside ROOT, which the boundary can write; a protected session could put a python3 there for the next launch to run outside the boundary; remove the entry from PATH, or move it after ENTRY, to launch with reserves`, and for the entry that supplies the program, such as one holding a `python3` wrapper script in the project, `the PATH entry DIR, which supplies python3, lies inside ROOT, which the boundary can write; a protected session could replace that python3 for the next launch to run outside the boundary; supply python3 from a PATH entry outside every path the boundary can write to launch with reserves`). The message names the entry, never what it holds. A project `bin` or `node_modules/.bin` that direnv or a shell profile puts on `PATH` before the directory that supplies `dirname` and `readlink` (normally a system directory such as `/usr/bin`) therefore refuses protected launches from that project. A virtual environment outside the working directory, every `--add-dir` and the account directory first on `PATH` works. While the run lasts, commands the launcher runs by name resolve only in the system directories; the native keeps the caller's `PATH`. The code-reach check has the limits listed for [protected Codex](codex-as.md#protected-mode), except that claude-as also checks `dirname`, `readlink` and the entry that supplies `python3`. The gate verifies the provider's certificates with Python's default trust store; `SSL_CERT_FILE` and `SSL_CERT_DIR` from the launch environment reach it, unchecked against the writable set, while Claude Code's own CA settings, such as `NODE_EXTRA_CA_CERTS`, do not apply to it.
- **Models**: the gate admits the Opus, Sonnet and Haiku families, including Claude Code's default, auxiliary and subagent models, and refuses a model whose usage has a row of its own, and every request when the usage report has a row the kit has not reviewed. A refused request gets HTTP 400 with a `quota reserve: ...` message, which Claude Code shows as an error.
- **Quota reads**: two reads (usage and profile, which proves the account and organization) per poll with the account's credential, which only the gate holds, in memory. Claude Code's start-up probe and title request are model requests and count against the quota. A credential that Claude Code rotates for the same account keeps the session; another account pauses it, and from then on every paused read checks the account's stored login with its profile read, never the signed-out credential, and reads no usage while the profile shows another account (or none), so the launcher says that a check passes, and F12 can resume, only once the enrolled account is signed in again. A start-up, rebind or continuation read whose profile shows another account stops before the usage request too. A window that has not started yet, which the usage report shows as 0% used with no reset time, counts as available, and its messages name no reset; any other window without a reset time is unavailable, which refuses the start or pauses the session.
- **Status line**: `CODING_AGENT_KIT_CLAUDE_PID` is the native's own pid. `CODING_AGENT_KIT_USAGE_FILE` is not passed, because the status line cannot write the metadata directory from inside the boundary, so `--info` keeps the usage of the last unprotected session; the gate's own readings drive the reserves.

## Codex account layout

Each account has a fixed entry point: `<codex_home>/accounts/NAME/auth.json -> <secrets_dir>/codex-NAME.json`, an absolute link. Account directories are 0700; complete credentials are 0600. `codex-as NAME` sets that account's `CODEX_HOME` and enforces file authentication; the first launch creates the account view itself, with no separate initialization command. Other arguments go to native `codex` unchanged after its own file-auth and SQLite flags (every command but `exec` also gets the update-check and `--no-daemon` flags), and the launched Codex keeps the caller's umask. `login` (except `login status` and help), `logout`, the daemon-only `agents`, `queue`, `app` (macOS and Windows), `remote-control` subcommands and `app-server daemon`, and remote or provider/auth settings are refused; `-p NAME` profiles work from `<codex_home>/NAME.config.toml`; root help or version, `help`, `update` and `completion` run as plain `codex`. See the [Codex verification record](codex-as.md) for the exact list and the remaining differences from native Codex. The root `<codex_home>/auth.json` belongs to native `codex`, desktop and IDE clients. codex-as never reads, checks or changes it, so the root login and each account keep independent token chains, even for the same ChatGPT user.

Private backups live at `<secrets_dir>/.codex-as-backup-*` and are excluded from completion. Permission errors name the exact path and are never fixed by an automatic chmod: the parents of `<codex_home>` and `<secrets_dir>` (both `$HOME` by default), `<codex_home>` and `<codex_home>/.tmp` must be owned real directories that are not group/other writable, and `<secrets_dir>` must be 0700. The account marker `<codex_home>/accounts/NAME/codex-as.initialized` and a private pending-setup record are fully written to temporary files before atomic publication, so an interrupted first launch can be retried; unknown existing directories are preserved and initialization is refused.

A root `<codex_home>/auth.json` that links into `<secrets_dir>`, and the root-level files `<codex_home>/codex-as.layout.json` and `<codex_home>/codex-as.initialized`, are not part of the codex-as layout. codex-as ignores those two files, so they can be deleted; the account marker in each account directory stays. Such a root link works, but it shares that account's token chain with the root clients, so a root login or logout revokes the account. To separate them, quit every root, desktop and IDE client completely, including the root app-server daemon and IDE extension app-servers, until `pgrep -af 'codex.*app-server'` lists none. Then remove only the link with `rm <codex_home>/auth.json` (the secrets file stays) and log in natively in the root home. A client that is still running keeps the old tokens in memory, and its logout (`account/logout`) revokes those cached tokens even after the link is gone, so quit it rather than logging out.

Credentials renew without a new login. The access token carries its own expiry; native Codex refreshes it when less than five minutes remain, and the server rotates the refresh token, which Codex writes through the account link into `<secrets_dir>/codex-NAME.json`. Only use triggers this refresh; no background keepalive runs. A revoked refresh token cannot be renewed and needs a new device login. **Native `codex login` and `codex logout` revoke the tokens of the current home's `auth.json` before removing it.** In the root home, a desktop or IDE logout included, that affects only the root's own login, unless that file is still a link into `<secrets_dir>` or a still-running client loaded its tokens through such a link; codex-as refuses both inside account views. A logout from inside an account's Codex (`/logout`) is native and still revokes that account's tokens; the launcher warns at exit with the steps below. Add accounts with `codex-as NEWNAME`. To replace a revoked account, move its secrets file aside under a name that does not match `codex-NAME.json`, then run `codex-as NAME`.

Config, both AGENTS files, rules, skills, agents, memories, session directories, history, the session index, and the complete SQLite home are shared. Database files and WAL/SHM use the original directory together, rather than individual file links. Configuration path fields must be absolute because native relative paths resolve against the account directory; the launcher reports the field name and never rewrites configuration. An explicit `sqlite_home` retains its absolute directory; otherwise, the root directory is used. Conflicting environment, project, or CLI overrides are refused.

Native thread writer locks and the rollout maintenance lock are shared. An active writer prevents another account from writing the same session. Interactive resume takes sessions over from the root daemon so another account can write them: it ends the old session and spawned agents there, temporarily archives them, restores saved archive visibility, then launches the selected account. An explicit `codex-as OTHER resume UUID` does this without a prompt for an idle session and asks first when it may be running, since takeover interrupts active work. `resume --last` takes over only the session it opens, the newest one native Codex lists, when that one is idle in the root daemon. Before the picker starts, the idle top-level sessions it lists by default (this directory, or the same place in a linked worktree; all of them with `--all`) are taken over and named, because the selection happens inside native Codex; they move to the top of the list. Sessions that may be running stay and are named too. Clients attached to the root daemon, such as Desktop, close a session taken over. The remaining daemon sessions stay loaded. Sessions held by standalone clients are never touched; native Codex shows its conflict screen until they exit. Explicit session names have account-path filtering problems, so the launcher rejects them and requests a UUID. Names can still be displayed and edited in the native UI.

Takeover requires a root daemon at 0.161.0 or newer, and a controlling terminal only to confirm a session that may be running. Unknown identities, unsafe sockets and ambiguous ownership cause refusal, and an unrecognized option in the resume command skips takeover. Recovery metadata stays private under `<codex_home>/accounts/.locks/UUID.handoff.json`; retain it and retry the same command after an interrupted or failed takeover. `fork UUID`, `exec resume UUID` and `exec fork UUID` never take over, but first finish an interrupted takeover of that UUID; `resume UUID` does too, and the picker and `resume --last` finish every interrupted takeover. Recovery only restores visibility. Saved history and original descendant archive visibility are preserved; unfinished runtime progress, SessionEnd hook effects and timestamp changes cannot be rolled back.

Cloud policy, the model catalog/cache, remote plugin installations/cache, MCP/Connector login, daemons, IPC, temporary files, and logs remain separate for each account. Local plugin paths in shared configuration can be shared. Remote plugin cache directories cannot be linked wholesale: one account's sync could delete another account's bundles. These existing root account caches are not imported into new accounts.

If account credentials are atomically replaced with a regular file, the link is restored when there are no other wrapper clients and the file matches secrets. If secrets have not changed during this run and the user identity matches, both copies are backed up, the new original bytes are imported, and the link is restored. If both copies changed, no startup snapshot exists, or identities differ, repair stops without guessing from timestamps. The last exiting client or the next idle startup can perform safe repair; repair errors do not replace the native exit code.

Divergence needs a manual choice while every client of that account is closed; the error prints both paths and the command. Back up `<codex_home>/accounts/NAME/auth.json` and `<secrets_dir>/codex-NAME.json`, keep the wanted copy at `<secrets_dir>/codex-NAME.json`, then restore the link with `ln -sfn <secrets_dir>/codex-NAME.json <codex_home>/accounts/NAME/auth.json`. Use the absolute paths the error or `codex-as --show-config` prints: the launcher compares the link text with them, so a link through a symlinked alias of the same directory is refused. A missing link is restored the same way, unless a logout inside Codex removed it: those tokens are revoked, so move the secrets file aside and run `codex-as NAME` to log in again. **Do not delete the account marker or overwrite either file with an older snapshot.** See the [Codex verification record](codex-as.md) for source and test limitations.

## Claude configuration and security boundaries

This section covers setup-token accounts, the default; a [native-login](#claude-native-login) account keeps Claude Code's own login instead. Tokens are saved at `<secrets_dir>/claude-NAME`: 0600, a regular file owned by the current user, with a single hard link. Daily startup sets only `CLAUDE_CODE_OAUTH_TOKEN` for the child and inherits the existing `CLAUDE_CONFIG_DIR`. It does not force `~/.claude`, preserving existing sources of `.claude.json`, MCP, configuration, and trust state.

Explicit API key/OAuth token/authentication FD/alternative provider/endpoint/profile overrides, authentication helpers in settings, and organization restrictions are refused. Only variable names or sources are reported, never values. Passthrough of login/logout/setup-token, `--bare`, authentication configuration source overrides such as remote/SDK/managed-settings/project-config-root, and unaudited options is prohibited. Only the first command operand is identified using native argument boundaries; words inside prompts are not scanned. Native Claude dispatches an exact first `auth` operand to authentication subcommands even with `-p` or `--`, so it is refused. Required/optional/variadic argument values retain their native roles. This is a bounded local CLI option check, without a promise of compatibility with every command.

Managed policy is respected: automatic enrollment stops for nonempty managed caches, system policy, policy helpers, authentication bindings, or profile loading chains that cannot be preserved. Empty or missing caches do not cause this refusal. The managed cache is checked at every enrollment.

New account files are created exclusively; incorrect permissions, ownership, symlinks, or hard links are refused. Account names must be nonempty, contain only ASCII letters, digits, underscores, and hyphens, and not start with a hyphen, as in codex-as. Local format validation is not server authentication; expired credentials are not automatically deleted or replaced through login.

## Account metadata

Both launchers keep a small cache of what they last saw about each account, so a completion preview or a person can look it up offline: `codex-as --info NAME` and `claude-as --info NAME` (`-i NAME`). It lives in `${XDG_STATE_HOME:-~/.local/state}/coding-agent-kit/accounts/` (an absolute `XDG_STATE_HOME` only; the directory is created 0700 on first use and must stay an owned, real 0700 directory), never in `secrets_dir`: a configuration whose `secrets_dir` is that directory is refused, and one that reaches it through a link is never read or written. Each file is a 0600 JSON object, replaced atomically and only when its content changes, with one writer:

| File | Content | Written by |
| --- | --- | --- |
| `codex-NAME.json` | email, plan, and the last usage snapshot | `codex-as`, before and after each run |
| `claude-NAME.json` | the label | `claude-as` enrolment or `claude-as --label` |
| `claude-NAME.usage.json` | the last 5-hour and weekly windows | `helpers/statusline.cjs` |

No file holds a token, and no time in them comes from the launcher's clock: a Codex snapshot carries the time of the rollout line it came from, a Claude one the time the status line saw it.

```text
$ codex-as --info work
work (Codex)
email   alice@example.com
plan    plus
5h      23% used, resets 14:30 (in 2h 10m)
weekly  41% used, resets Mon 09:00 (in 3d 4h)
seen    12 min ago
```

Times are local. A window whose reset time has passed reads `reset since HH:MM`; missing data reads `not recorded yet`, and an account without a label reads `not set (claude-as --label NAME LABEL)`. `--labels` prints one line per account, `NAME<TAB>LABEL` (the email for Codex, the label for Claude) or the bare name when there is none; the zsh completions use it as descriptions. Both queries, like `--list`, create no directory, run no preflight or native CLI and never open a credential: they read only the state files, accept only an owned regular 0600 file with one link, at most 64 KiB, with unique keys, and print only the fields above with control characters removed. An unsafe file fails `--info` with one line that never quotes it; `--labels` shows that account's bare name.

- **Codex identity**: the email (the `email` claim, else the profile claim's `email`) and the plan (`chatgpt_plan_type`) from the account's `id_token`, decoded locally at each launch and again after the run. An API-key login records the plan `API key` and no email. The plan changes only when Codex refreshes the token.
- **Codex usage**: after native Codex exits, codex-as reads the session rollouts modified during the run, only regular files (never a FIFO, device or link), and keeps the newest `token_count` event with rate limits of the default `codex` family timestamped within the run. A rollout counts when its thread is the one the run resumes (`resume UUID`, `exec resume UUID`; a fork writes a new thread, so its source never counts), or when its `session_meta` names this account's ChatGPT user and workspace as the creator. The resumed thread comes first, then the newest rollouts: codex-as reads the tail (at most 1 MiB) of up to eight of this account's, after the first lines of at most 64 others. Of concurrent runs of one account the newest snapshot normally wins: each run reads the stored record only just before it replaces it. Times from the year 10000 on are ignored. The windows are named by their length (300 minutes is `5h`, 10080 is `weekly`). This is best effort, silent on failure and never changes the exit code. Known gaps: the rollout format is Codex's internal one, so a change leaves usage blank; a session switched inside Codex (`/resume`) is missed; compressed rollouts (`.jsonl.zst`) are skipped; past 64 other accounts' rollouts modified during the run, this account's own new session can be missed; and another account that resumes, during the run, a thread this account created can be counted here.
- **Claude label**: a new account asks `Label for this account (optional, e.g. your email):` after the confirmation and before any token exists, and saves the label only after the token. Control characters, more than 100 characters and anything containing `sk-ant-` are refused, so a pasted token is never stored. `claude-as --label NAME LABEL` sets the label of an existing account, `claude-as --label NAME` asks for it on `/dev/tty`, and an empty label clears it.
- **Claude usage**: Claude Code gives the status line its rate limits only for Pro and Max subscribers and only after the first API response; headless `claude-as NAME -p` runs render no status line and record nothing. claude-as passes its child `CODING_AGENT_KIT_USAGE_FILE` (the path of `claude-NAME.usage.json`), `CODING_AGENT_KIT_TOKEN_ID` (the first 16 hex digits of the token's SHA-256) and `CODING_AGENT_KIT_CLAUDE_PID` (its own pid, which stays the session's because it execs claude), and drops inherited values first. Claude Code passes `CLAUDE_CODE_OAUTH_TOKEN` to none of the commands it starts, the status line included, so `helpers/statusline.cjs` recognises the session by that pid: it records only when all three are set and the claude with that pid runs it, as its parent or behind one shell (`sh`, `bash`, `zsh`, `dash`, `ksh` or `fish`; read from `/proc` on Linux and with `ps` elsewhere). A claude started inside the session has a pid of its own and records nothing, whatever it inherited. A token that is visible all the same must hash to the identifier. For a `native-login` account, whose credential claude-as never reads, the identifier comes from its enrollment instead, so a token that is visible never matches it. In protected mode `CODING_AGENT_KIT_CLAUDE_PID` is the native's own pid, since the launcher stays running, and `CODING_AGENT_KIT_USAGE_FILE` is not passed (see [protected Claude Code](#protected-claude-code)). The path must be absolute with a `claude-NAME.usage.json` name in an owned 0700 directory, and the numbers are valid; it writes when the windows change or the record is older than five minutes, never on Windows, and its printed status line is unchanged.

Privacy: emails and labels appear in completion previews, screen shares and recordings, and the output of `--info` lands in any agent transcript that runs it. No token is ever printed or stored there.

## Completion, installation, and concurrency

`install.sh` links the zsh completions into `PREFIX/share/zsh/site-functions`, which must be on `fpath` before `compinit` runs (with oh-my-zsh, before it is sourced; the installer prints the line), and the Bash completions into the bash-completion user directory, `${BASH_COMPLETION_USER_DIR:-${XDG_DATA_HOME:-~/.local/share}/bash-completion}/completions`, where bash-completion autoloads them. For the first argument Bash runs `codex-as --list-accounts` or `claude-as --list-accounts` and zsh `--account-labels`, which adds each account's email or label as its description, so the launchers must be on `PATH`; the listing enumerates only safe filenames and metadata, without reading credentials, running the native CLI, or using the network, and an invalid configuration offers nothing. Corrupt contents are detected at startup. A first argument that starts with `-` completes the [own options](#own-options) instead. After `-i`, `--info` or `--account-info`, and `claude-as --label` or `--set-label`, the next argument completes account names the same way, in zsh in the group `Codex accounts` or `Claude accounts`; nothing else follows an own option. The completions call `--list-accounts` and `--account-labels`, the spellings every release from 0.3.0 on accepts, so a shell opened before an update or after a rollback keeps completing. Before `NAME`, `--reserve-5h` and `--reserve-weekly` complete their values (`off` and every tenth percentage, then every whole percentage that matches what is typed) and then the remaining flag or the account names, and `claude-as --enroll-native` completes an account name. After `NAME`, later arguments first complete the supported scope, then delegate to existing native completion when available; Bash hands the native completion the command line from `NAME` on, with the cursor, the current and the previous word adjusted to it.

fzf-tab, when present, uses the same candidates; normal Tab works without fzf. New terminals load the new completions; nothing appends source or PATH lines to rc files. Installation only creates links and triggers no real initialization, login, or model requests.

The launcher's own step/help headings are cyan, confirmations/warnings yellow, successful saves/initialization green, and errors red. By default, color is enabled only for the terminal receiving the message; redirected logs stay plain. Confirmations on a separate `/dev/tty` can still use color without affecting redirected Codex/Claude output. `CODING_AGENT_KIT_COLOR=auto|always|never` is supported (unset or any other value means `auto`); nonempty `NO_COLOR` or `TERM=dumb` takes priority and disables color. Native command output, completion account lists, and internal machine output are not colorized.

**Codex supports concurrent sessions across accounts and different sessions within one account.** Each wrapper and native child holds a shared account lease; credential repair requires an exclusive lease. Suspended processes or a child surviving an abnormal supervisor exit still block repair. Account lease files persist and are not deleted based on PIDs; per-session takeover leases are removed when the takeover ends. A shell inheriting `CODEX_HOME` from account A can launch B directly, but the inherited source must be a verified managed account directory. Before Codex 0.167.0, the native same-account OAuth refresh semaphore is in-process only and saves truncate and rewrite the secret, so several processes can refresh at once or briefly read partial JSON; 0.167.0 and newer serialize their own commits through native lock files and replace the secret atomically (see [symlink writeback verification](codex-as.md#symlink-writeback-verification)). The wrapper implements no additional OAuth. Direct CLI, desktop, and IDE clients do not participate in wrapper leases, and automatic exit repair cannot exclude them. Manual repair requires closing that account's clients. Processes are not automatically killed, quotas are not switched automatically, no background keepalive runs, and Claude tokens are not renewed.

```sh
tests/codex-as.sh

pre-commit run --all-files
```

Routine tests use temporary HOME directories, fictitious credentials, and fake CLIs. They cover Bash/zsh, TTY, stdin/JSON stdout, link repair and interrupted setup, root auth isolation, concurrent leases, signals, refresh writeback, incorrect permissions, completion secrecy, the configuration file, launcher location and `install.sh`. When Codex 0.161.0 or newer is installed, an additional real Codex offline app-server fixture checks legacy/paginated history, shared SQLite discovery, native writer locks and token refresh writeback through the account link against a local token endpoint, without login or model calls and with zero other requests. A missing or older Codex explicitly skips this check. Native protocol tests do not verify real-account server authorization, quotas or token lifetimes, and do not directly operate the terminal picker/`--last`.

The protected-mode suites drive the gate, the monitor, the supervisor and both launchers against `127.0.0.1` fixtures with fabricated credentials and fake natives, and run whole launches on a PTY inside the real boundary where the host provides it (otherwise those cases skip and say why). With codex-cli 0.167.2 on `PATH`, and with Claude Code 2.1.322 as `KIT_REAL_CLAUDE=/path/to/claude` or on `PATH` (Linux only), they also run the real natives inside the boundary against the fixtures. They cannot show how a real account's usage reports behave: identity fields, rounding, rate limits and token lifetimes are not covered.
